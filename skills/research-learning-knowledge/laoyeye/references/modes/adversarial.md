# 成型方案对抗审查

用于明确压力测试一个已有主张、计划或方案；不冒充专业代码 diff / Trellis 规划审查。输入为可被证伪的主张、目标、机制、证据和约束；主张尚不清晰才补问。

1. 先准确复述最强版本，拆开事实、假设、推断和价值取舍，避免攻击用户没有主张的弱版本。
2. 从底层约束检查因果链、数量级、边界条件、激励、依赖与替代解释。挑最多三个最可能推翻结论的攻击点，不堆小毛病制造严厉感。
3. 每个攻击点写“被攻击前提 → 失败机制 → 证据或缺口 → 可证伪实验”。逻辑不充分不自动说明结果错误；反方也承担举证责任。
4. 给明确 verdict：成立、需修改、目前证据不足或被反证；列幸存结论、必须修改部分和最小下一步。判断强度与证据相称。

特别检查隐性共享状态、顺序依赖和部分完成的安全性；有委托时计入交接、上下文重建、审阅与返工成本，明确集成责任。审阅对照原任务与实际产物，不能只看 diff 自洽；用故意漏做部分要求的样例检验验收是否会红。优先找权限、数据损失、重试 / 幂等、并发、版本偏差和静默失败中的高代价风险。证伪实验应尽早、低成本且能明确区分假设，不能用“全部跑完看看”代替。

默认先分析再交付，不把它变成访谈。只有用户明确要求盘问，才逐轮问最关键前提，等待回答再追下一层；不偷用设计树 frontier 或苏格拉底六问规则替代其节奏。

缺资料时交条件 verdict 和需要的证据，不伪造反证。实验仅设计，不自动运行；不移植来源中的专属模型、费用、调度频道或外部联系规则。最强风险已覆盖就停。
