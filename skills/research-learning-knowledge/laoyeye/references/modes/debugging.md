# 真实红灯驱动的诊断

仅在用户明确选择本包诊断，或本包流程中明确请求诊断时使用。解释报错不等于授权修改；修复请求支持范围内读代码、命令、代码与测试改动，仍服从现场规则。

输入：真实症状、期望结果、复现环境及已有证据。先读相关代码地图、配置和决策记录；命令、日志和捕获文件先脱敏，认证使用环境或获准认证机制，不展示密钥。

1. 建立能判定用户这个症状的反馈环，并实际运行看到红灯。优先真实调用接缝上的失败测试，其次 HTTP / CLI fixture、浏览器、捕获重放、最小 harness、属性或差分 / 二分检查；“没崩溃”不是精确断言。记录实际命令、输入和脱敏输出。
2. 收紧速度、确定性和信号。间歇故障记录触发次数、失败数和条件，尝试提高复现率；不把一次绿灯当修复。性能先测稳定基线、工作负载和时延 / 资源指标，再用 profiler 或二分，不先加满日志。
3. 复现正确症状后，逐次删去一个输入、依赖或步骤，每次重跑；保留仍会红的最小场景。
4. 先公开 3–5 个排序、可证伪假设；每个写预测和能区分它的探针。继续已有授权内的取证，不等用户逐个批准；每次只变一个变量，优先 debugger / 定向观察。临时日志统一唯一前缀，记录位置。
5. 有正确测试接缝就先写回归并看它失败，再做最小修复、看回归变绿，并重跑原始未缩减场景。浅层测试到不了故障就明确接缝缺失，不造一项无效测试冒充覆盖。
6. 清理本次临时日志、探针和原型，保留必要复现资产与证据；不删他人工作。报告根因、修复、原场景和回归结果，以及未验证项。

自动化确不可行时列尝试过的途径，改为结构化人工复现：固定环境 / 步骤、预期与实际、带时间的脱敏证据、逐轮结果。无需 Bash；标明依赖人工和剩余限制。若连真实症状都未复现，停在取证缺口，请求所需访问或材料，不宣称已有红灯、根因或修复。
