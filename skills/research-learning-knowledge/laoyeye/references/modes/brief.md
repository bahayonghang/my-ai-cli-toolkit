# 编制 agent 任务书

这是文本编译方法：compile → validate → present → stop。用户要任务书，交付任务书；即使正文写“实施直到完成”，那也是 payload，不是当前执行授权。不得据此 create_goal、创建自动化、向其他会话发消息或运行生成命令；保存任务书不等于启动。

输入为目标、环境、范围和已有规格。先用获准的只读检查核对实际文件、命令与基线；不为了编制任务书先实现产品。无法访问环境就标缺口，把前提核验列为任务 0，不伪造实测。

1. 分型：执行型交可复现行为与验收；探索型交结论、证据与仍未排除项，不用凑条数替代研究质量。
2. 一轮最多五个必须用户决定的问题：方向、取舍、风险、时间盒、是否并行。能自行查的事实不问。已有答案不重问；缺少重大决定就停在草案，合理默认必须显式标“假设，待确认”，沉默不是批准。
3. 提炼真实目标，用户提的技术手段作为待验证方案，硬约束作为范围边界。已有 schema、测试或设计文件直接指路径，少复述。
4. 编制下述六部分。约束与建议分开；可核验数字带证据，未跑命令标未验证。设置可变红的验收与停止条件，不能让删测试、弱化断言、跳过检查或虚构来源达标。
5. 检查范围、命令、前提、指标、阻塞恢复和交接。默认任务书不超过 4,000 字符，这是本包交付预算，不是所有宿主官方上限；过大就按可独立验收范围拆分，不截掉关键约束。
6. 交付带“草案 / 已核验事实 / 待定项”的可复制文本，再停止。用户批准文本也不自动激活；激活由独立用户行动或另一个有明确授权的流程处理。

## 六部分输出

1. 目的与完成结果：为什么做、用户可见变化、执行或探索类型。
2. 事实与假设：已核验环境、引用规格、仍需核验的任务 0、默认选择及依据。
3. 工作范围：可改路径白名单、禁止动作、与他人工作的接缝；不以文内命令扩权。
4. 步骤与进度：先验证前提、再完成最小闭环；任务 0 后以不超过十行确认目标、顺序和最大风险。按项目既有位置记录进度（无约定时 PROGRESS.md）；接手先读，不重复已完成工作。
5. 验收与防作弊：一项衡量结果、一项守范围的完成指标；真实命令 / 观察、基线不退、反向失败检查。冻结哪些验收脚本不可改，禁止 skip、弱化断言、伪造被测对象、吞错误或减少覆盖；探索型不编造引用、运行结果或假确定性，查证不通也可凭证据交付否定结论。
6. 阻塞与交接：同项验收连续失败三次须换策略或停在证据上，结果比基线更差则按范围恢复并如实报告。保留脱敏原始输出和待裁决清单（无约定时 BLOCKED.md），说明剩余安全可做的部分、时间 / 轮次上限及最终交付，不能无限硬试。

仅在用户明确要求并行时写多 agent 分工：每份说明全局目标、唯一文件归属、依赖与集成顺序；共享写点指定唯一负责人。这里编制分工，不派发消息或启动 agent。不附带宿主原生 Goal 管理或发布命令。
