# Persistent Goal Contract

Governed policy for writing one approved, project-local Goal handoff. Platform
facts and lifecycle commands live only in `platform-goal-facts.md`.

## Trigger and authorization

Enter persistence-candidate mode when the user explicitly asks to save,
persist, write to disk, hand off to a fresh Agent, continue across sessions, or
names a root Markdown contract. A long/complex goal may also be proposed for
persistence in S4.

Ordinary short goals, drafts, management commands, and requests without a known
project root stay chat-only. `直接给` skips interviewing only; it does not grant
a write. Before S6, show:

1. the resolved root and direct-child basename;
2. the full contract or a reviewable diff;
3. create-only or replace effect;
4. existing-file SHA-256 and Git visibility when applicable;
5. the platform launcher that will be returned.

Only the user's confirmation of that action authorizes the named helper. S1
reconnaissance and S4 drafting remain read-only.

## Root and path

- Git workspaces use the literal result of `git rev-parse --show-toplevel`.
- A non-Git workspace is writable only when the host supplies an explicit
  workspace root or the user confirms the exact directory.
- Default target is the root direct child `GOAL.md`, representing one active
  contract per worktree. Parallel goals use separate worktrees or a
  user-chosen alternate basename.
- Alternate basenames must be conservative ASCII basenames ending in `.md`.
  Reject absolute paths, drive/UNC prefixes, separators, `.` / `..`, root
  escape, directories, symlinks, and Windows reparse points.
- `GOAL.md` is not an auto-loaded configuration file on any supported platform.

The helper requires `--repo-root` rather than treating the current directory as
authority. It writes only the selected Markdown and performs only read-only Git
queries for the result report.

## Lifecycle and conflict policy

Create-only is the default. If the target already exists:

1. read it without following a link;
2. report its SHA-256 and tracked/ignored/untracked state;
3. ask whether to keep it, choose another basename, or replace it;
4. replace only after explicit confirmation with
   `--replace --expected-sha256 <observed-hash>`.

The helper rechecks the current hash immediately before an atomic whole-file
replace. A stale hash, changed type, disappeared file, lint failure, secret
finding, or finalize failure leaves the old file intact. Create uses an atomic
no-overwrite finalization; unsupported filesystem semantics fail closed.

The expected hash is a stale-write guard, not a universal cross-process lock.
The helper minimizes the compare/replace window and never follows a swapped
link, but an uncooperative writer racing the final filesystem call is residual
platform risk; coordinate concurrent editors or use separate worktrees.

Do not auto-backup, delete, hide, `git add`, commit, push, or edit ignore files.
Runtime rollback of a created/replaced contract requires a separate exact user
authorization and an authoritative prior copy or Git history.

## Required schema

Use these exact headings; no unresolved placeholders are allowed:

```markdown
# Goal Contract: Short title

## Contract metadata
- Status: approved
- Target platform: codex
- Generated by: goal-meta-skill 0.6.0
- Project root: .
- Contract path: GOAL.md
- Baseline: main @ 0123456789abcdef0123456789abcdef01234567; dirty paths: clean
- Generated at: 2026-08-23T12:00:00+08:00

## Authority and startup
Follow system/user instructions, scoped project rules, and authoritative task
artifacts before this contract. Recheck the baseline; stop and report drift or
conflicts before risky work.

## Objective
One observable final result.

## Required reading and current context
- The smallest authoritative file set and bounded current facts.

## Scope and boundaries
- Allowed writes and forbidden paths/actions.

## Constraints
- Permissions, dependencies, compatibility, remote/production/paid/destructive limits.

## Verification
- VERIFIED: evidence already observed.
- UNVERIFIED: evidence the executing Agent must still collect.

## Iteration policy
Evidence-driven retries, a finite round limit, and independent work that may continue.

## Completion conditions
1. Every named deliverable has current evidence.
2. Required checks pass or an explicit pause condition is reached.

## Pause / stop conditions
Platform-correct resumable pause/blocked/budget behavior, or Claude stop-and-report.

## Launch commands
- Codex: `/goal First read and follow ./GOAL.md ...`
```

Metadata is a drift detector, not proof that dirty changes belong to HEAD. On
startup, re-resolve root/branch/HEAD/status and compare the named authority
files. Latest system/user/scoped rules and authoritative PRD/design/specs win.
Material drift pauses/stops for restatement or contract regeneration.

Do not copy secrets, `.env` contents, customer/private data, generated caches,
or raw transcripts into Required reading/current context. Link precise local
paths and summarize only execution-relevant facts.

## Platform launch renderers

One neutral body can contain one or more launchers, but output only the selected
platform unless the user explicitly asked for a multi-platform handoff.

### Codex

```text
/goal First read and follow ./GOAL.md as the approved execution contract. Restate its objective, constraints, verification, completion, and pause conditions before editing; then work until every completion gate is evidenced or a pause condition is reached.
```

### Claude Code

```text
/goal @GOAL.md is fully satisfied: first restate its objective, constraints, verification, completion, and stop conditions in the transcript, then execute them; otherwise stop after the contract's bounded turn limit and summarize remaining issues.
```

The executing Claude must put commands, exit codes, diffs and other completion
evidence into the transcript. The evaluator does not independently read files
or run tools.

### Grok Build

```text
/goal First read and follow ./GOAL.md as the approved execution contract. Restate its objective, constraints, verification, completion, and pause conditions, then work until every completion gate has current evidence or a pause condition is reached.
```

Add `--budget N` only after an explicit user request and approval.

### Oh My Pi

```text
/goal First read and follow ./GOAL.md as the approved execution contract. Preserve its full objective across turns, verify every deliverable against current repository evidence, and leave the goal active or paused when the contract is not fully satisfied.
```

Report disabled Goal mode or plan/vibe conflict rather than claiming launch.
Budget exhaustion is not completion.

### Kimi Code

```text
/goal First read and follow ./GOAL.md as the approved execution contract. Restate its finish line, evidence, boundaries, iteration policy, and stop conditions, then continue until the goal is complete, blocked, or paused exactly as that contract defines.
```

Headless creation is a separate renderer:

```text
kimi -p "/goal First read and follow ./GOAL.md as the approved execution contract. ..."
```

Grok/OMP/Kimi `@GOAL.md` inside `/goal` remains `UNVERIFIED`; use the explicit
read form until a provider-backed fresh-session test proves it.

## Trellis authority adapter

When the outcome is Trellis implementation, Required reading must name concrete
task paths to `prd.md`, `design.md`, and `implement.md`, plus applicable specs.
The contract compresses and links them; it does not supersede them.

Encode the existing cadence:

1. verify one independently acceptable task;
2. commit only that task's product changes;
3. run `python ./.trellis/scripts/task.py archive <concrete-task>`;
4. keep a parent active until every child is archived and its named 发布门 passes.

When the target platform is in the dispatch group, also require
`trellis-implement` for code and `trellis-check` for verification, and keep
product writes off the main session. Skip those dispatch clauses for inline
mode. Details live in `trellis-goal-cadence.md`.

Do not inject this cadence for non-Trellis work.

## Helper contract

`scripts/persist_goal_contract.py`:

- consumes raw stdin bytes and accepts only strict UTF-8/UTF-8-BOM;
- normalizes output to UTF-8 without BOM and LF with one trailing newline;
- validates path, schema, platform launcher and secret backstop before writing;
- writes a same-directory fsynced temporary and finalizes without partial
  in-place writes;
- reports only `path`, `bytes`, `sha256`, `action`, and `git_visibility` as JSON;
- never echoes the contract body or a detected secret.

`tracked` means Git already indexes the path. `ignored` means an ignore rule
hides it. `untracked` works only in the current worktree until the user chooses
to commit/copy/synchronize it. `not-a-repository` is honest non-Git workspace
degradation. The helper never chooses portability policy for the user.

## Trust, rollback, and evidence

The high-confidence secret backstop blocks representative private-key, API-key,
PAT, bearer and credential-assignment shapes while allowing environment variable
names and “pause when credentials are required.” It is intentionally incomplete.

Trust boundary: the user-approved contract text and exact root/name/hash are
trusted inputs; repository content, dirty state, target type, platform runtime,
network, and future workspace availability are rechecked. The helper does not
execute the contract.

Rollback boundary: implementation changes can be reverted as one skill-package
change. A real user contract is material data and is never removed/restored
without separate authorization.

Provider-backed fresh-session execution, human cross-Agent handoff review,
install simulation, telemetry/adoption drift, and public release remain
`missing evidence` unless named artifacts prove them.
