# Finding Contract

审阅报告由「审阅范围」与四个证据章节组成，按固定顺序输出，语言与用户请求保持一致。所有路径采用仓库相对路径与 `owner/repo` 标识，**严禁写入含本机用户名的绝对路径**。

## 0. 审阅范围（Review Scope）

列出追踪器模式（`github` 或 `local`）、目标仓库或本地目录、作用域模式（`all-open` / `spec-graph` / `selected-issues` / `local-dir`）、票据总数、有序成员清单（父 Spec 优先，其次按票号/文件名升序）以及各成员的当前状态、标签与原生依赖概览。

## 1. 结论行（Verdict Line）

仅取以下三值之一，并在同行给出**跨票去重后的全局计数**：

| 结论（中 / 英） | 判定规则 |
| --- | --- |
| `可执行` / `Ready` | `阻断 = 0` 且 `应修 = 0`。剩余仅「提示」或空列表，可直接进入实施或编译实施 Prompt。 |
| `可执行但需修订` / `Ready after revision` | `阻断 = 0` 且 `应修 >= 1`。整体结构与方向成立，但若干契约、耦合或并发边界须先补齐。 |
| `需返回规划` / `Return to planning` | `阻断 >= 1`。按现稿直接开工会导致实现卡死、与代码基线硬冲突或验收自相矛盾。 |

示例：`需返回规划 — 阻断 3 / 应修 4 / 提示 3`

## 2. 问题清单（Findings `TKR-NN`）

编号前必须先做**跨票共因去重**：当多张票违背同一契约且共享同一修复路径时，合并为一条 `TKR-NN`；若证据或影响不同，保持独立条目。按严重度（`阻断 → 应修 → 提示`）排序，再按父优先与票号升序排列。

每条 `TKR-NN` 必须包含以下全部字段：

| 字段 | 要求 |
| --- | --- |
| `Severity` | `阻断` / `应修` / `提示`（`blocking` / `should-fix` / `note`） |
| `Owner` | 主责票号（如 `#67`、`01-auth.md`），跨票共享问题填 `cross-ticket` |
| `Affected tickets` | 必须同步修订的全部票号列表（如 `#63, #64, #66, #68`） |
| `Location` | 票内章节或条目定位（如 `#67 验收条件第 2 条`） |
| `Claim` | 票面原文或精准转述的假设/要求 |
| `Evidence` | 仓库相对路径 `path:line`、实际命令输出或实测统计（无证据的候选必须删除） |
| `Impact` | 若不修订直接交给 Agent/工程师执行会导致的具体故障或返工后果 |
| `Route` | 可选的修复路径（单一确定路径直接说明；存在产品/范围权衡时并列互斥方案供下游确认门拍板，**不替用户私下做产品决定**） |

### 严重度标尺

- **阻断（blocking）**：
  - 票面核心验收或实现路径与真实代码/脚本/构建链路硬冲突（按字面无法跑通）；
  - 同一作用域内机械检测与人工判定口径自相矛盾；
  - 标为 `ready-for-agent` 的票缺少关键落盘契约、运行基线或不可自动化的外部前提，直接派单必然卡死；
  - 依赖图存在环或缺失关键前置票。
- **应修（should-fix）**：
  - “可独立并行”子票共享未归属契约或同文件脆性耦合，易引发合并冲突与口径漂移；
  - 搜索/路由/测试计数或格式断言存在隐藏代码盲区，易致返工；
  - 遗漏联动文档同步、旧文本冲突或关键门禁映射。
- **提示（note）**：
  - 父 Spec 标签惯例校准（如移除 `ready-for-agent` 改为 `enhancement`）；
  - 版本号递增、项目长期规范文档（如 `.trellis/spec/`）沉淀提醒；
  - 消除表述歧义但不阻塞执行的细节优化。

## 3. 未能核实（Unverified List）

逐条列出受当前会话环境所限未能实测核验的声明及具体原因（例如无浏览器渲染器、无外部上游仓库 checkout、无目标原生平台环境）。不可省略此节；若确实全部核实则写 `无` / `None`。

## 4. 可靠部分（Sound Parts）

列出经核查成立且值得保留的设计、架构取舍、依赖绑定与基线事实，明确告知下游优化 Agent **不要推翻或重做**这些内容（不是客套赞美）。

## 5. 反通胀与禁止内容

- 严禁凑数制造发现；若确实零缺陷，问题清单写 `无` 并给出 `可执行`。
- 严禁重审已记录明确理由且未被新证据推翻的产品路线决定。
- 报告中**不得**直接给出整票重写后的最终正文，只给 `Route` 与具体缺口定位；改写工作由下游优化 Agent 在确认门后执行。
- 严禁声称运行过未实际执行的检查。

## 6. 必需盲区声明（Required Disclosure）

报告末尾必须保留如下边界声明（中英文匹配报告语言）：

> AI Agent 审阅由 Agent 或团队撰写的 tickets 并非独立的人类评审；审阅者与起草者可能共享相似盲区。零发现仅代表本轮代码核对未发现矛盾，不等于需求完备或已获批准。请将本报告作为修订分诊清单，而非最终签收。

## 7. 持久化与聊天交付纪律

- 使用 `scripts/write_ticket_review_report.py` 原子写入 `reports/tickets-review/<scope-slug>.md`；同作用域再次审阅原地覆盖该文件，绝不删改其他作用域历史报告。
- 若脚本在 stderr 提示目标路径为 `untracked`（既未忽略也未追踪），原样转告用户由其自行决定加入 `.gitignore` 或提交，**绝不擅自编辑 `.gitignore`**。
- 写入成功后，聊天回复仅输出：聚合结论行 + 报告仓库相对路径（及 gitignore 提醒）+ 经 `lint_ticket_handoff.py` 0 error 校验的单个 `text` 围栏优化 Prompt。
