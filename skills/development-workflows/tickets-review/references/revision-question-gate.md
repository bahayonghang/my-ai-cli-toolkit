# Reviser Confirmation & Remote Write-Back Gate

本门禁约束**消费 Handoff Prompt 的下游优化 Agent**，不改变本审阅技能（`tickets-review`）本身的只读边界：审阅者自身不提问、不改票、不写代码、不启动实现。

## 1. 写回前先做三类分诊

下游 Agent 读完本地报告 `reports/tickets-review/<scope-slug>.md` 与受影响票据后，将剩余待处理项分为三类：

1. **第 1 类 — 仓库可查事实**：通过读源码、单测、脚本或 `git` 即可确认的事实。**禁止向用户提问**，直接查证。
2. **第 2 类 — 唯一技术修订路径**：不改变产品范围、不改变权限/交付边界、且 `TKR-NN` 的 `Route` 只有唯一明确改法的契约对齐（如补写计数口径说明、修正锚点、补充 `docs-sync` 步骤）。**禁止仪式性提问**，直接纳入本轮修订。
3. **第 3 类 — 用户所有权决策与对外写回授权**：
   - 改变任务范围、交付物集合或新增工具/脚本接口的决策；
   - `TKR-NN` 的 `Route` 列出两个及以上互斥方案（例如“新增构建参数” vs “手工同步加合成单测”）；
   - 将票据标签从 `ready-for-agent` 降级为 `ready-for-human`，或调整验收降级准出条件；
   - **远程 GitHub Issues 写回授权**（默认保守策略：除非用户启动优化会话时已显式授权“直接修改远程 Issues”，否则必须将写回确认合并进本批提问）。

## 2. 宿主结构化提问铁律（禁止甩清单干等）

只要存在第 3 类项，必须在执行任何 ticket 写回前调用宿主结构化提问工具**一次收口**（最多 4 题，每题标出推荐项与互斥选项）：

| 宿主 | 实际结构化提问工具 |
| --- | --- |
| Claude Code | `AskUserQuestion` |
| Antigravity | `ask_question` |
| Oh My Pi | `ask` |
| Codex | 当前会话实际暴露的 `request_user_input` 或等价工具（不得臆造工具名） |
| 其他 / 无工具 | 单条简短编号提问 |

- **严禁 Dump-and-Wait**：禁止把确认项写成聊天长文清单然后坐等用户提醒“请用提问工具”。
- **严禁仪式性提问**：若不存在第 3 类项（且本地模式或远程写回已明确授权），直接执行修订，不得多问一轮。

## 3. 远程写回与回读核验（GitHub 特有安全边界）

1. **禁止命令行内联长正文**：尤其在 Windows PowerShell 中，向 `gh issue edit` 传中文正文极易出现编码损坏或引号截断；必须先由脚本或 UTF-8 LF 文件写出正文，再使用 `gh issue edit <n> --body-file <tmp-utf8-file>`。
2. **跨票原子同步**：同一 `TKR-NN` 涉及多张 `Affected tickets` 时，必须在同一轮依次更新所有受影响票据及其原生 `sub_issues` / `blocked_by` / `labels`，不能只更新父 Spec 而留下子票漂移。
3. **写回后回读**：每张改过的远程或本地票据必须回读正文、标签与依赖摘要，确认无乱码、无截断、无遗漏。
4. **严格边界**：修订完成后立即停止并按 `TKR-NN` 汇总结果；**绝不修改业务代码、绝不编辑审阅报告本身、绝不关闭 ticket、绝不开始实施**。
