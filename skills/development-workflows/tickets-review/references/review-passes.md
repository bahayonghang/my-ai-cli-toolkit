# Review Passes (Pass 0–7)

本技能将审阅拆为 **Pass 0（机械预检）** 与 **Pass 1–7（代码实证判断）**。核心原则：只汇报有代码/脚本/CLI 证据支撑的真实缺陷，不凭直觉泛泛评价文风。

---

## Pass 0 — Mechanical Precheck（机械预检）

由 `scripts/ticket_precheck.py` 执行，决定仅凭字符串、依赖图、文件系统与只读 Git/GitHub API 可判定的事实：

- **图结构完整性**：缺失被引用的父票或子票、依赖成环（cycle）、重复票号、PR 编号误入 Issue 作用域。存在这些错误时脚本返回退出码 `1`，必须 **Fail-Closed** 汇报并停止，不得继续生成报告。
- **元数据与一致性信号（非致命，交由 Pass 6 评估）**：
  - 父 Spec（含下挂子票）同时贴有可执行标签（如 `ready-for-agent`），可能导致自动领票脚本误领父 Spec；
  - 正文 `Blocked by:` / `Part of #` 与 GitHub 原生 `blocked_by` / `sub_issues` 不一致；
  - 票据正文为空或残留未替换模板占位符（如 `TODO`、`TBD`、`<fill-me>`、`[placeholder]`）；
  - 票内引用的仓库相对路径或 GitHub permalink 文件/提交在当前仓库中不存在；
  - 目标报告路径 `reports/tickets-review/<scope-slug>.md` 的 git 状态（`ignored` / `tracked` / `untracked`，仅作提醒，绝不阻断）。

## Pass 1 — 代码与测试契约核对

**核心问题**：票面提到的文件、符号、CLI 子命令、数据通路、基线计数和既有测试约束，是否与当前代码库真实一致？

**核查方法**：
1. 针对票面列出的每个模块、脚本、CLI 命令与规则编号，直接检索并精读对应源码及单测，不依赖记忆。
2. 逐项验证隐含假设：
   - **数据通路**：票面要求“搜索支持某字段/别名”，实查 `search` 代码是否真的读取了该配置源（例如搜索函数只读主索引而不读路由 overlay）。
   - **构建/重建能力**：票面要求“离线可重复重建”，实查构建脚本是否支持脱离外部上游 checkout 的局部重建模式。
   - **双口径计数**：核对公开展示计数（如过滤掉 deprecated/superseded 后的可见数）与底层索引/单测硬编码全量计数是否一致。
   - **格式与命名硬断言**：检查现有测试是否对标题节名、换行符、禁止字面量或表结构有强校验。

**典型判定**：若票面指令按字面实施必然触发既有单测失败、命令报错或死路，定级为 `阻断` 或 `应修`。

---

## Pass 2 — 机械检查与人工判定边界

**核心问题**：票面要求的“自动化断言 / 可执行走红 / 测量反例”与仓库现有静态检测器的能力边界是否一致？

**核查方法**：
1. 核对票面提到的规则/门禁 ID 在现有 linter/checker 代码中属于**机械检查（脚本可测）**还是**人工/模型判定（仅文档条款）**。
2. 检查父 Spec 的边界声明（例如“不扩展静态扫描器职责”）与子票验收条件（例如“覆盖一个测量反例并让可执行检查走红”）是否存在自相矛盾。
3. 核对“补齐输出断言”是否混淆了**纯 Schema 校验的评测 JSON**（只检结构不跑逻辑）与**可运行红绿单测**。

**典型判定**：同一作用域内对验证载体自相矛盾，导致执行者无所适从或擅自塞入脆弱启发式规则时，定级为 `阻断`。

---

## Pass 3 — AFK 可执行性与前置契约完备度

**核心问题**：标为 `ready-for-agent`（或计划交由无人值守 Agent 执行）的每张票，前置契约与运行环境是否真的自洽？

**核查方法**：
1. **产物落盘契约**：若多张票要求新建样例、夹具或参考文件并由下游验收票汇总，检查是否明确了统一存放目录、命名规范、是否提交进 Git，以及是否会意外触发全仓扫描器报错。
2. **外部环境前提**：若验收依赖浏览器渲染器、截图对照、运行改动前旧版基线、独立无上下文子代理复核或原生 GUI 窗口，核查票面是否写明获取方式与缺失环境时的降级准出条件。
3. **版权与素材来源**：若引用了外部仓库或示例，核查许可证状态是否已明确，且要求原创内容而非复制无证素材。

**典型判定**：缺少运行前提或汇总路径却标为 `ready-for-agent` 的票，建议明确补齐前置契约，或将标签调整为 `ready-for-human`（作为 `Route` 选项提交确认门）。

## Pass 4 — 跨票并发冲突与共享契约归属

**核心问题**：宣称“可独立实施”的多张票，是否暗含未声明的共享契约、高频同文件冲突或脆性位置耦合？

**核查方法**：
1. 找出父 Spec 提出的新增共享概念（新状态枚举、公共报告字段、前置步骤格式），核对是否明确了由哪张票负责定义与落地。
2. 映射每张“可并行”子票大概率修改的文件清单；若多张票共同修改同一核心规范/提示词/索引文件，检查是否存在**按行号或题号映射的耦合区域**（例如改了基础问题列表的编号会静默破坏变体替换规则）。

**典型判定**：共享契约归属悬空或并行改写会破坏既有联动契约时，定级为 `应修`（严重时 `阻断`），建议在父 Spec 锁定共享字面量或增加先后依赖边。

---

## Pass 5 — 验收标准（AC）子句可测性与耦合盲区

**核心问题**：把每条 AC 拆成独立子句后，能否得到唯一明确的 pass/fail 判定？有没有遗漏联动文档或旧规则冲突？

**核查方法**：
1. **按子句拆解**：一条 AC 常捆绑 2–3 个子条件（如“同步计数、接口、文档与路由覆盖”）；逐一核对每项在仓库中对应的真实文件与命令（如文档生成同步命令 `docs-sync`）。
2. **联动旧文本扫描**：用代码搜索检查仓库内其他参考文档、Keep 清单、测试夹具是否保留了与新票相冲突的旧表述；若漏列联动修改点，实施后会留下文档内自相矛盾。
3. **范围外声明自洽**：确认“Out of Scope”列表没有与某张子票的隐含工作量打架。

---

## Pass 6 — 元数据、标签与依赖拓扑

**核心问题**：追踪器上的标签、父子归属、阻塞关系和收尾契约是否准确？

**核查方法**：
1. 对照仓库 `docs/agents/triage-labels.md` 及历史同类已关闭 Spec，核查父 Spec 是否误贴 `ready-for-agent` 等单票执行标签。
2. 核对 Pass 0 报出的原生 `blocked_by` 与正文声明漂移，及 Pass 4 发现的隐性顺序依赖是否应补加阻塞边。
3. 核查版本号递增（如 `SKILL.md` / `package.json` version）与项目长期记忆/契约文档（如 `.trellis/spec/`）沉淀是否在收尾票中交代清楚。

---

## Pass 7 — 基线漂移与在研 PR 检查

**核心问题**：自票据起草所锚定的 commit 以来，目标模块是否已发生变更，或存在尚未合并的开放 PR 与其重叠？

**适用时机**：票据含 commit permalink/时间戳，或 `ticket_precheck.py` 检测到存在开放 PR 或目标路径较新提交时。

**核查方法**：
1. 运行只读 `git diff --stat <anchored-commit>..HEAD` 检查变动是否触及目标模块。
2. 检查开放 PR 列表的分支名、标题与关联 Issue，标注潜在冲突或已覆盖内容；若未触及目标模块，记入「可靠部分」作为实证基线。
