# 用本地 Codex CLI 审查代码并留存 Markdown 报告

GitHub 跟踪：[父单 #70](https://github.com/bahayonghang/my-ai-cli-toolkit/issues/70)。下表的本地 01–04 分别对应 GitHub #71–#74。

## 问题与方案

开发者希望在同一仓库连续几次请 GPT 审查代码，再让另一个 agent 逐条复核。聊天摘要没有固定位置，单看当前 diff 也不能代表整个仓库。提供名为 `codex-review` 的第一方技能，明确选定 Git 范围，实际调用本地 CLI，返回可直接打开的报告。

## 用户故事

1. 提交前，我可以让 GPT 一起检查暂存、未暂存和未跟踪改动，包括尚无提交的仓库。
2. 全仓审查时，我可以看见送审的文件、跳过的文件以及跨批次分析的限制。
3. 我可以指定 commit 或基线分支，只检查相应的已提交变更。
4. 我可以指定 GitHub PR 编号或链接，在当前工作区有改动时仍得到该 PR 版本的报告。
5. 我可以指定交互、动效等关注点，同时区分源码推断和需要运行界面确认的现象。
6. 接手的 agent 可以通过项目内路径、版本或内容指纹找回同次审查，定位问题，验证影响。
7. 如果 CLI 失败、证据为空或只完成部分审查，我可以从报告识别这个状态。

## 实现决定

- 使用当前项目中实际安装的 Codex CLI；模型读取 Git 选取的证据。保留每次运行自己的报告文件。
- 无明确范围时优先使用未提交改动；干净工作区说明范围为空。仅在用户明确要求时扩展到全仓。
- PR 固定 base/head 和合并基点；不切换用户分支。基线比较使用 merge-base，合并提交以第一父提交为参照。
- 审查输出包含范围、送审证据、运行状态、带位置和验证方法的问题。附带材料只作为评审依据；修复、发表评论、合并和发布属于单独操作。

## 验收与测试

通过同一个命令行入口，在隔离 Git 仓库构造可区分的暂存、工作区、未跟踪文件、分叉历史和失败的审查进程。核对模型实际收到的数据和磁盘报告。真实 CLI 用小样本检验发现、路径和可复核性；PR 单独核验 GitHub 元数据和 Git 对象。模型质量、视觉体验和跨平台运行的结论以实际证据为准。
